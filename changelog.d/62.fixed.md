Fix the probes that promised a server answer the server does not give, and two mixins listed in an order that made their own implementation dead code. `supports_data_type_postgres_jsonpath`, `postgres_xid8`, the six `postgres_*multirange` probes and `postgres_macaddr8` were unconditional `True` on types that arrived in PostgreSQL 12, 13, 14 and 10 respectively — a gate that cannot say no tells the dialect it can render the type on any server, and the disagreement arrives at execution, with the DDL built and sent, and the error naming a table rather than the version gap that caused it. `supports_jsonb_subscript` claimed 14.0+ for a capability PostgreSQL does not have at all (SQL subscripting covers arrays and composites; jsonb is read with `->`/`->>` or the SQL/JSON path language) and now answers `False` unconditionally, and `supports_json_arrow_operators` returned `True` unconditionally, advertising on 9.2 — where the operators do not parse — an arrow the core formatter would happily render; it is now gated at 9.3. The four version floors were measured against the scenario servers rather than read off the release notes, because the notes and the servers disagreed about jsonpath: the notes say 13, and 12 has it. `PostgresArrayEnhancedMixin` is now listed before the core `ArrayMixin` and `PostgresUUIDMixin` before the core `UUIDMixin`, where each answers `True` to a question the core answers `False` for; listed in the backend block, the core default was what every caller actually saw and the backend's implementation was unreachable. Each fix is pinned by a test in both directions, so a versioned type cannot again answer yes unconditionally while `text`/`integer`/`varchar` saying yes remains correct on purpose.
